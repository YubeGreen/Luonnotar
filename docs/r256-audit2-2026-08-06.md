# r256 二次源码审计（2026-08-06）

## 结论

第一次 r256 源包不是可直接接受的最终候选。二审发现了会影响真实行为的错误，已在本候选中修复；当前可进入完整 Gradle 构建与真机 A/B，但不能在这两项完成前宣称问题已根治。

## 第一包发现并修复的问题

1. Shell 会探测 main 与 persistent，却只解冻 main；现改为命中哪个先解冻哪个，并在 shield 中处理所有已观察到的 GMS 目标。
2. 首击去抖是全局的；persistent 紧接 main 时可能吞掉第二条。现按进程分别去抖。
3. `cmd activity unfreeze` 错误附带 `--user 0`。现 direct 语法与 `am` fallback 分离。
4. direct 失败后部分 Kotlin 路径没有 fallback。现统一退回 `am unfreeze`。
5. shield 的 48 次上限按“批次”计数，一批可能实际发两条命令。现按真实目标调用计数。
6. probe 每个 sequence 只上报一次，可能永远停在首次 `absent/frozen`。现状态变化也会上报。
7. 混合可见性会被过早判成 thawed。现任何未观测 PID 都令整体保持 unobservable。
8. 没有外部 `timeout` 时命令可能无限挂起。现有约 1 秒内置 watchdog。
9. sticky/目标配置热变更不会重启 sidecar；无 READY 的活进程也会被当健康。现加入兼容性检查与 3 秒 READY 超时。
10. stale reader/process 可能在 watcher 替换后写入状态。现所有回调都核对具体 process identity。
11. 临时恢复与已验证 thaw 共用一个去重集合，后续真实 thaw 可能不计数。现拆成两套 sequence 集合。
12. 后处理提交失败仍占用 cooldown。现提交失败回滚预约。
13. GlobalFreezerOff 原流程容易在未重启时采集，并可能无法精确恢复原始 override。现保存状态、核对 boot_id、分两阶段执行并精确恢复。
14. episode 只按 120 秒硬截止重置；软租约结束后 120 秒内的新故障会错误继承旧额度与截止时间。现软租约结束即建立新 episode。
15. cgroup v1 的 `FREEZING` 过渡态未视为冻结。Shell 与 Kotlin 现同时识别 `FREEZING/FROZEN`。
16. StickyUnfreeze 没有动作时，`sticky-actions.json` 可能成为空文件。现始终写入合法 JSON 数组。

## 已执行的验证

- 源包路径与归档成员检查：无绝对路径、`..` 穿越、设备文件或符号链接。
- 版本字段检查：versionCode 78、engine 256、config schema 7、status schema 17。
- Shell：生成、`sh -n`、双目标连续事件、direct→am fallback、无外部 timeout 的 watchdog。
- Kotlin：命令/协议/policy harness；特权核心与完整 UserService 使用最小 Android stub 编译。
- 工具：现有 Python 单元测试；PowerShell 脚本做静态结构检查。
- 密钥扫描：归档不包含 keystore、签名属性或明显的私钥材料。
